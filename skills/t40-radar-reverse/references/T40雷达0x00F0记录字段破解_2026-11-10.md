# T40 雷达 0x00F0 记录字段破解（内存数据逆向）

2026-11-10 · 承接《T40雷达0x00F0逆向总结_2026-11-10.md》第九节「第一优先」

> 与《T40雷达0x00F0头部与源数组补全_2026-11-10.md》互补：那一份讲的是「上游」——
> 头部各字节的写入指令、A/B/C 被 `0x4CA7C` 从 `0x0C3C1940 / 0x0C4233C0 / 0x0C419780`
> 拷进来、再上游是 DSP 解码循环 `0x4C888`；本文讲的是「下游验证」——用 `snap12.txt`
> 里的内存快照把每条记录逐字段复算回去，以及由此得到的转速可读性。

---

## 一、结论

**12 字节记录里那 6 个 u16 全部解出来了。** 它们不是雷达原生的量，而是固件把三组
float 数组定点化之后的结果——所以之前拿统计方法怎么试都对不上，因为中间隔着一次
`×1000 / ÷100` 和一次 `+2π` 偏置。

源数组和构造函数都在这次的内存转储里：

| 名字 | 地址 | 内容 | 元素 |
|---|---|---|---|
| 帧缓冲 | `0x0C442FB0` | 19 字节头 + N×12 记录（payload 在 +8） | — |
| 索引表 | `0x0C451A30` | `u16[10000]`，记录 i → 数组下标 | 2 B |
| A | `0x0C456850` | `{float az; float el; float r}` | 12 B |
| B | `0x0C473D10` | `{float inten; float inten2; float ?}` | 12 B |
| C | `0x0C4911D0` | `u32` µs 时间戳 | 4 B |

字段（`tv` = 索引表给出的下标，常态 `tv = i`）：

| 字段 | 公式（固件原样） | 物理含义 | 单位 | 量程（实测） | 置信度 |
|---|---|---|---|---|---|
| c0 | `trunc(A[tv].x * 1000)` | **方位角** | mrad | 1031 ~ 5204 | 确定 |
| c1 | `trunc((A[tv].y + 6.28319) * 1000)` | **俯仰角**（+2π 偏置） | mrad | 5000 ~ 7200 | 高 |
| c2 | `trunc(A[tv].z * 1000)` | **斜距** | mm | 1400 ~ 62000 | 确定 |
| c3 | `trunc(B[tv].x / 100)` | **回波强度**（线性） | ×100 定点 | 8 ~ 7009 | 中 |
| c4 | `trunc(B[tv].y / 100)` | **第二强度量**（SNR 候选） | ×100 定点 | 3 ~ 657 | 中 |
| c5 | `(C[tv] - t_us_b_low16) & 0xFFFF` | **该点时刻相对本圈起点** | µs | 0 ~ 65535 | 高 |

反解公式（写解析器用这个）：

```
az = c0 / 1000                     # rad
el = c1 / 1000 - 6.28319           # rad，负值常见
r  = c2 / 1000                     # m
x  = r*cos(el)*cos(az)
y  = r*cos(el)*sin(az)
z  = r*sin(el)
t  = c5                            # µs，同一波束的所有点共享同一个值
```

> xyz 只是**显示用的约定**。固件内部在 `0x422C8` 里用的是极角形式
> （`x = R·sin(θ)·sin(a)`、`z = R·cos(θ)`，θ = π/2 − 仰角 时与上式等价）。
> 实测也支持上式：同一波束的 10 个点 z 全在 0 附近、xy 展开到 60 m，
> 这是一条水平射线，不是竖直线。

## 二、怎么破的：从 64 KB 栈跨到构造函数

上一轮卡在「`0x13298` 的调用者返回地址在 64 KB 之外」。这次 `bbxspy2.c` 把
`[fp, 栈顶)` 整段落盘（68.6 KB），再用「前一条指令必须是 BL/BLX」筛，
在 `+0x10000`（正好是 `0x13298` 那个 `0xFFD4` 栈帧之上）捞出两个候选：
`0x30864` 和 **`0x4CE5C`**。

`0x4CE5C` 的上下文里有这么两句：

```asm
0x4CE34  movw r5, #0x2fb0
0x4CE38  movt r5, #0xc44        ; r5 = 0x0C442FB0
0x4CE50  ldr  r1, [sp, #0x28]
0x4CE54  add  r0, r5, #8        ; r0 = 0x0C442FB8  ← payload 起点
0x4CE58  bl   #0x307dc          ; 发出去
```

`0x0C442FB8` 正是内存转储里那个 `03 10 07` 的位置。于是问题变成「谁引用
`0x0C442FB0`」——扫全 ELF，**只有 `0x4CBF8` 一处**。这就是构造函数。

它的常量池（`0x4D060`）把最后几个未知量也交代了：

```
0x4D064  f = 1000.0        ← 角度/距离的比例因子
0x4D068  f = 6.28319       ← 2π，加在 c1 上
0x4D06C  f = 100.0         ← c3/c4 的比例因子
0x4D070  = 0x0C451A30      ← 索引表
0x4D074  = 0x0C456850      ← 数组 A
0x4D078  = 0x0C473D10      ← 数组 B
0x4D07C  = 0x0C442FB8      ← 帧 payload
```

这四个地址和之前 `dd` 出来的 `table0 / A / B / count` **一字不差**——转储地址选对了。

## 三、构造函数在做什么

`0x4CBF8` 的逻辑（简化）：

```c
void build(void) {
    static u8 call;                 // [0xC442FB0]  每 3 次调用才真干活
    if (call % 3) { call++; return; }
    call++;

    u8 batch = base[4], nbatch = base[5];
    if (batch >= nbatch) { /* 攒够一轮，重置 */ }

    u16 total = *(u16*)(base+6);            // 本帧点数
    if (batch == nbatch-1) {                // 最后一批：条数 = total - 5000*batch
        nrec = total - 5000*batch;
        memset(payload, 0, 19 + 12*nrec);   // ← 先清零，再逐条填
    }

    u16 *tab = (u16*)0x0C451A30;
    u32  slot = 5000u * batch;              // 表/数组的窗口起点
    for (i = 0; i < nrec; i++) {
        u16 tv = tab[(slot + i) & 0xFFFF];
        float *a = (float*)(0x0C456850 + 12*tv);
        float *b = (float*)(0x0C473D10 + 12*tv);
        u32   *c = (u32*)(0x0C490E78 + 0x358 + 4*tv);   // = 0x0C4911D0
        u16 *r   = (u16*)(payload + 19 + 12*i);
        r[0] = (u16)(a[0] * 1000.0f);
        r[1] = (u16)((a[1] + 6.28319f) * 1000.0f);
        r[2] = (u16)(a[2] * 1000.0f);
        r[3] = (u16)(b[0] / 100.0f);
        r[4] = (u16)(b[1] / 100.0f);
        r[5] = (u16)(*c - t_us_b_low16);
    }
    payload[13] = nrec * 12;
    payload[15] = batch_cap;  payload[16] = nbatch;
    payload[17] = sum8(payload+19, 12*nrec);      // 记录区校验
    payload[18] = sum8(payload+1, 17);            // 头校验
}
```

三个关键点：

1. **`vcvt.u32.f32` 是截断，不是四舍五入。** 所以 `1.4668 → 1466`，`5.2047 → 5204`。
2. **c1 加了 2π 再乘 1000。** 仰角本来是 ±1 rad 的小量，加上 2π（6.28319）后变成
   5.28~7.28 的正数，直接当 u16 存，省掉了符号位。
3. **`memset` 先清零再填。** 这正是内存转储里那些「全 0 记录」的来源——不是
   丢包，是 dump 抓到了写一半的帧。

## 四、四条硬证据

### 4.1 两个校验和（`+17` / `+18`）

之前猜了 40 个起点试 CRC32 全不中，因为它根本不是 CRC：

```
payload[17] = sum8(记录区)          # 覆盖 12*N 字节
payload[18] = sum8(payload[1..17])  # 覆盖 17 字节
```

- 现场抓包 `bbx_180s.jsonl`：**2766/2766 帧双校验通过**。
- 12 份内存快照：**完整的 4 份（@@@1/4/6/9）全中，撕裂的 8 份全不中**——这本身
  就是佐证：memset 之后没写完，和当然对不上。

### 4.2 逐条精确对上（决定性）

快照 `@@@ 4`（`captures/snap12.txt`）里，记录 18~28 与 `A[18..28]` **连续 11 条、
三个字段一字不差**：

```
rec18 ( 5204, 6314, 1507)   A[18]*1000 = ( 5204, 6314, 1507)  OK
rec19 ( 5204, 6314,13403)   A[19]*1000 = ( 5204, 6314,13403)  OK
...
rec28 ( 5204, 6361,59242)   A[28]*1000 = ( 5204, 6361,59242)  OK
```

同一份快照里 `A[i]` 对不上的那些记录（rec0~rec17）是**上一圈**的点——`struct`
先 dump、`A` 后 dump，中间隔了几毫秒到几十毫秒，雷达已经换了一帧。这也是为什么
之前的统计方法永远差一点点：不是字段错，是两份数据不同源。

### 4.3 c3/c4 与 B 数组同形状

快照 `@@@ 4` 的记录 18~28：`c3 = 6511, 587, 490, 376, 283, 250, 225, 213, 196, 158, 144`
数组 B[0..10]：`6211, 678, 508, 427, 359, 310, 274, 254, 207, 166, 158`

同一条波束、逐点同序、量级差 3% 以内（差的是那一圈的目标变化）。B 的下标整体错位
18 条——因为 B 是后 dump 的，写指针已经往前走了。`@@@ 0` 里还抓到过一次**完全精确**
的：`rec14 c3,c4 = (49,16)` ↔ `B[14]/100 = (49,16)`。

### 4.4 c5 是 µs（顺手把转速变成可读量）

c5 有三个很强的性质：

1. **同一波束的所有点共享同一个 c5。** 一帧里 `az=1031` 的 10 个点 c5 全是 10147。
2. **c5 与方位严格线性**，斜率 = 1/ω。

于是可以直接从一帧里反推转速，不需要 CAN：

| 抓包 | 每帧条数 | c5 反推 | 设定/实测 |
|---|---|---|---|
| `bbx_180s.jsonl` | 58 | **928 rpm**（p10~p90 = 927~930） | 900 / 905 |
| `bbx_1800rpm_30s.jsonl` | 36 | **1847 rpm**（p10~p90 = 1844~1853） | 1800 / 1800 |

两档都稳定在 2.5% 的同一偏差上（928/905 = 1.025，1847/1800 = 1.026），说明这是
CAN 上报值或 µs 基准的系统性刻度差，不是随机误差。

**这一条还反过来印证了「一帧一圈」**：`bbx_180s` 帧周期 180/2766 = 65.09 ms，
按 928 rpm 一圈是 64.6 ms —— 比值 1.007。

## 五、19 字节头：全部落定

| 偏移 | 类型 | 含义 | 依据 |
|---|---|---|---|
| +0..2 | u8×3 | `03 10 07` 魔数 | 常量 |
| +3..4 | u16 | seq，每帧 +1 | `strh r0,[r4,#0xb]` |
| +5..8 | u32 | µs 计数器 A | `str r8,[r4,#0xd]` ← `[0x0C49AE14]` |
| +9..12 | u32 | µs 计数器 B，**低 16 位是 c5 的基准** | `str r2,[r4,#0x11]` ← `[0x0C451A2C]` |
| +13..14 | u16 | `N*12`，记录区字节数 | `strh r2,[lr,#0x15]` |
| +15 | u8 | 分批容量（常态 1） | `strb r1,[r4,#0x17]` |
| +16 | u8 | 批数 `ceil(点数/5000)`（常态 1） | `strb r2,[r4,#0x18]` |
| +17 | u8 | `sum8(记录区)` | 见 4.1 |
| +18 | u8 | `sum8(+1..+17)` | 见 4.1 |

补充：A 与 B 两个 µs 计数器相差约 2.95 s（同一台机器上稳定），说明它们不是同一个
时钟，或者是同一条流水线上两个不同阶段的打点。两者的 Δ 都是 ~65,000/帧，即 **1 MHz**。

## 六、顺带解决的老问题

| 老结论 | 现在 |
|---|---|
| `+17` 是未知的高熵字段 | **记录区和校验**（和，不是 CRC） |
| 尾部没有 CRC32 | 对，校验在头里，不在尾 |
| c5 与 c0 比值 10.19，「只有量级关系」 | 那是 **µs vs mrad**：比值 10.19 ⇒ 937 rpm，1000 rpm 时 1 mrad 走 9.55 µs |
| 内存快照里有全 0 记录 | 构造函数先 `memset` 再填，dump 抓到写一半 |
| `0x13298` 的调用者够不到 | 栈 dump 到 `+0x10000` 就找到了；`0x4CE5C` 指向构造函数 |
| 「每转一圈一帧」 | 确认：帧周期 ≈ 一圈，但**只有 239° 有数据**（c0 固定 1031→5204），其余是空档 |

## 七、还没确定的

1. **c3/c4 的物理名。** 公式确定（`B0/100`、`B1/100`），行为确定（沿波束随距离单调
   衰减，1.4 m 处 6511 → 59 m 处 144）。但「功率」还是「SNR」需要找到写
   `0x0C473D10` 的代码——那个数组不是被字面量引用，是通过指针传进去的，静态搜不到，
   得再插桩一次。
2. **A 的第二个 float 为什么加 2π。** 只能确定取反后是 ±1 rad 的小角度；是俯仰还是
   别的角（比如波束内的相位），要看 A 的填充者。
3. **5000 分批何时触发。** 正常帧 `nbatch=1`，走「最后一批」分支，一次发完；
   `5000` 是单包上限（60 KB）。没抓到过多批次的帧，说明这种模式要么没启用，
   要么只在补传黑盒时出现。
4. **t_us_a 与 t_us_b 差 2.95 s 的来源。** 两个 1 MHz 计数器不同步，差值是常数。

## 九、一句话总结

**6 个 u16 = 方位(mrad) / 俯仰+2π(mrad) / 斜距(mm) / 强度×2 / µs 时间差**，
全部是固件从三组 float 数组定点化来的；构造函数在 `0x4CBF8`，源数组在
`0x0C456850 / 0x0C473D10`，索引表在 `0x0C451A30`。**现在可以离线把 0x00F0 直接
还原成点云了**，剩下的只是 `c3/c4` 该叫功率还是 SNR 这种命名问题。
