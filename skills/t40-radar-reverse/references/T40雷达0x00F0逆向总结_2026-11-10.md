## 一、这份报告在讲什么

目标是把 DJI T40 植保机 RD2484R 雷达的**原始点云通道 `0x00F0`（blackbox_over_net_v2）**解出来：
它多久发一次、载荷怎么排、12 字节一条的记录里每个字段是什么，最终能不能直接拿来画点云。

**当前状态：全解了。** 时间维度、容器格式、**记录里 6 个 u16 的来源与物理含义**都已确定，
并用运行期内存 + 采集数据双向验证过。做法是拿新写的宽窗口 shim 越过 64 KB 栈帧，
找到真正写记录的那个函数（0x4CBF8），再把它读的三个全局数组从 `/proc/<pid>/mem` 里挖出来。
详见**第十一节**——直接看那节就够，前面五、六节是当时没解出来时的统计推断，留作对照。

## 二、链路现状与访问方式

```
雷达 RD2484R ──USB(AR1021x)── 板卡 FZ3B ──以太网── 电脑
               192.168.8.2      192.168.8.1/24
                                192.168.1.254/24
```

- 板子在这个阶段**不是 AP**：MT7612U 一直没插，电脑走的是网线 `192.168.1.254`。
  雷达那一侧由板卡的 AR1021x 起 `radar_wifi`，板卡自己当 AP（192.168.8.1）。
- 从电脑进雷达要**从板卡跳**：`ssh -p 107 root@192.168.8.2`（root/root）。
  板卡没有 sshpass，用 `SSH_ASKPASS` + `setsid -w` 喂密码；雷达没有 `scp`、没有 `base64`，
  传文件只能 `ssh 'cat > /tmp/x' < 本地文件`。
- 板卡重启后 `/tmp/ap.sh` 会丢，脚本里要先重建，否则跳板全挂。
- 板卡时钟停在 2021-08-31，日志时间戳不可信；时间分析一律用板卡 `time.monotonic_ns()`。

## 三、时间维度：每转一圈一帧

### 3.1 基准采集

180 秒、905 rpm、板卡单调时钟打点（`captures/bbx_180s.jsonl`，2766 帧 0x00F0、5730 帧 0x1E61，CRC 错 0）。

| 项目 | 值 |
|---|---|
| 平均速率 | **15.36 帧/秒** |
| 等价周期 | 65.09 ms |
| 间隔 min / p50 / mean | 46.75 / 60.39 / 65.09 ms |
| 间隔 p1 / p99 / max | 52.86 / 81.91 / 86.57 ms |
| 标准差 / 变异系数 | 8.81 ms / 0.135 |

**所有间隔都落在 46~87 ms，一次都没超过 100 ms** —— 所以它不是“攒一批再分块发”，是连续流。

### 3.2 节拍是「3 短 1 长」

| 簇 | 数量 | p10 | p50 | p90 |
|---|---|---|---|---|
| 短拍 | 2057 | 58.7 ms | 60.1 ms | 61.3 ms |
| 长拍 | 708 | 78.5 ms | 79.6 ms | 81.4 ms |

长拍占 25.6%，且几乎总是三个短拍跟一个长拍：3×60 + 80 = **260 ms 一个超周期，正好 4 帧**。
180 秒里每 30 秒的帧数是 461/461/462/460/461/461 —— 0.135 的变异系数几乎全部来自这个固定节奏，
不是随机抖动。

### 3.3 每圈三样东西：2 帧 1E61 + 1 帧 0x00F0

- 1E61 自身成组：按 <10 ms 聚类，2826 组里 2544 组是 2 帧。
- 每组里恰好 1 帧 0x00F0；0x00F0 距**上一个** 1E61 的 p50 只有 **0.6 ms**，
  距**下一个** 1E61 的 p50 是 59.2 ms。

```
[1E61 帧1] —0.2~2ms→ [1E61 帧2] —0.6ms→ [0x00F0] ——~60ms——→ 下一圈
```

### 3.4 转速扫描：确实是锁相的

`tools/bbx_rpm_sweep.py`，每档等 6 秒稳定、测 15 秒，实测转速取自 CAN 上的 `0x1E0F`：

| 设定 rpm | 实测 rpm | 0x00F0 帧/秒 | 1E61 帧/秒 | 0x00F0 中位间隔 | 帧/圈 |
|---|---|---|---|---|---|
| 600 | 601 | 5.21 | 21.70 | 199.35 ms | **0.52** |
| 900 | 905 | 15.35 | 31.84 | 60.51 ms | **1.02** |
| 1200 | 1198 | 20.45 | 40.99 | 42.00 ms | **1.02** |
| 1500 | 1501 | 25.56 | 51.19 | 39.96 ms | **1.02** |
| 1800 | 1800 | 30.63 | 61.32 | 38.63 ms | **1.02** |

结论：**900 rpm 以上严格一帧一圈**，速率与转速成正比。600 rpm 是例外，掉到两圈一帧，
说明雷达内部还有个约 190 ms 的下限节拍——做密度实验别低于 900。

### 3.5 1800 rpm 下的两路交替

1800 rpm 时每帧的记录数中位 36（905 rpm 是 59，约六成），而帧率翻倍，总量基本持平。
更关键的是 `+7` / `+11` 两个计数器：905 rpm 下几乎每帧都 +1（2766 帧里各只有 20 帧没动），
**1800 rpm 下变成严格交替——+7 只在奇数帧 +1，+11 只在偶数帧 +1（各 461/920）**。
按“本帧谁 +1”分组比较内容，记录数、c1 范围、c3 最大值、c5 分布全都一样，
所以不是两路不同数据，更像同一个流被拆成两半轮流发。

## 四、容器格式：19 字节头 + N×12 记录（已定死）

### 4.1 它其实不分片

三条互相印证的证据：

1. 每帧载荷长度 `len % 12 == 7`，2766/2766 帧成立。
2. 头部 `+13` 的 u16 **精确等于 `载荷长度 - 19`**，2766/2766 帧成立，且永远是 12 的倍数——
   固件自己把“后面有多少字节的记录区”写在了头里。
3. 尾部没有 CRC32：换 40 个起点去试“尾 4 字节 = CRC32”零命中，`19 + 记录区` 正好用干净。

所以 `dji-agras-radar` 文档里“最后一片附 frame_crc32”在这版固件上不成立，
**解析时不需要重组，一帧就是完整一份**。

### 4.2 19 字节头逐字段

| 偏移 | 类型 | 实测行为 | 置信度 |
|---|---|---|---|
| +0 / +1 / +2 | u8 | 常量 `03 10 07` | 确定 |
| +3 | u16 | 帧序号，每帧严格 +1（2765/2765，无跳变） | 确定 |
| +5 | u8 | 高熵（256 种取值） | 未解 |
| +6 | u8 | 缓慢递减（增量众数 −1 / −2） | 未解 |
| +7 | u16 | 计数器，每帧 +1（2744/2765，20 次停住、1 次 +2） | 高 |
| +9 | u16 | 905 rpm 下每帧 −488 或 −397 两个离散档；1800 rpm 行为突变 | 未解 |
| +11 | u16 | 计数器，每帧 +1（2746/2765，19 次停住） | 高 |
| +13 | u16 | **记录区字节数（= N × 12）** | 确定 |
| +15 / +16 | u8 | 常量 `01 01` | 确定 |
| +17 | u16 | 高熵（2709 种取值） | 未解 |

三个 +1 计数器互相独立：`(+7−+3)` 和 `(+11−+3)` 都在缓慢漂移，各自独立停住过，不是同一个值。

## 五、12 字节记录：观察到什么、否掉了什么

### 5.1 形状

按 6 个 u16 看（记录内 `+0/+2/+4/+6/+8/+10`）：

```
54 14 | 3d 18 | 93 05 | 4e 00 | 0d 00 | 61 cf
 c0      c1      c2      c3      c4      c5
 5204    6205    1427    78      13     53089
```

| 字段 | 值域 | 行为 |
|---|---|---|
| c0 | 1031..5204（帧内） | 帧内递增，连续相同会把记录分成 10~15 条的「块」；每帧都从 ~1031 到 ~5204 |
| c1 | ~5000..7200 | 小幅摆动，同一块内基本恒定 |
| c2 | 0..65535 | 块内递增（~2500/条），16 位回绕，最像角度量 |
| c3 | 8..7009 | 块内单调递减（从几百降到几十） |
| c4 | 3..657 | 与 c3 同步递减，c4/c3 中位 0.207 |
| c5 | — | 与 c0 同量级（比值 p50 = 10.19），块内恒定 |

### 5.2 被数据否掉的假设

| 检验 | 结果 | 结论 |
|---|---|---|
| c0 是不是 1 秒回绕的 16 位定时器 | 4173×15.36 ≈ 64100 ≈ 65536，很像 | **否**。换 1800 rpm 一测，帧率翻倍而 c0 跨度仍是 4173 tick 一个不差 → 跟「每帧扫过的范围」绑定，不是时间 |
| c5 是不是 c0×10 | 残差有 706 种取值，范围 −271..1280 | **否**，只有量级关系 |
| c4 是不是 c3 的定比 | c4/c3 从 0.117 到 0.885 | **否** |
| c2 在帧内是否排序 | 相邻递增只占 51.1%（随机是 50%） | **否**，整体不排序，只有块内局部递增 |
| 0x00F0 是不是 1E61 的超集 | 每帧记录数中位 58 vs 点数中位 6，总量比 **9.9 : 1** | 方向上成立：0x00F0 是过滤前的原始点，1E61 是抽稀后的结果（对得上 1E61 那串距离/仰角/点数过滤器） |

## 六、固件侧：挖到哪里、断在哪里

### 6.1 已有的东西

- `/home/root/app.elf`，1,491,188 字节，md5 `0d33f0dfbc5fc00f711362fcc56ef307`，
  ELF32 / ARM / 小端 / **已 strip** / 非 PIE（装载基址 0x8000，所以文件偏移 = 地址 − 0x8000）。
  已备份在 `captures/app.elf` 和 `captures/radar_backup/home_root_2026-11-02.tgz`。
- 雷达是 glibc 2.18 —— 这条决定了插桩怎么做（见 6.4）。

### 6.2 静态挖到的

**路由表 @0x0B3740**（16 字节一项 `{key, mask, device, name_ptr}`）：

```
061D0000  FFFFFF00  00C00001  000C9560   ← blackbox_over_net_v2
06120400  FFFFFF00  00C00001  000C9550   ← perception_over_net_v2
```

**字段名 schema 表**（.rodata 0xC6xxx–0xC7xxx，格式是「类型字符串 + 字段名」交替）：
`pcl_count` / `pcl_total_num` / `time_us_tf` / `radar_point_cloud(power, snr)` /
`radar_pcl_avoidance_plane(plane0..3, vplane0..2)` /
`time_us_index|cluster|process|transmit|avoid`（全 uint64）/
`detect_cluster_63(posx,posy,posz,nrpx,nrpy,nrpz,hgta,hgtr,bazi,bele,bdis,disx,disy,disz,lens,pmid,pmin,pmax,cfar)`。
**这张表和 0x00F0 的 6 个 u16 对不上**——表里多是 float，0x00F0 是整数，说明它用的是更底层的一套结构。

### 6.3 发送路径（动态 + 静态互相咬合）

```
[某业务函数]  ──?──▶  0x13298  打包并发送（开 0xFFC8≈64KB 栈缓冲）
                        │  bl 0x13B30(ch)  → 协议描述符
                        │  blx [desc+0xc] → 打包函数（V2 = 0x16464）
                        │  bl 0x11C8C ─(全是尾调用 b)─▶ 0xF4D0 ──▶ sendto@plt(0x9D98)
                        └─ sendto 的调用点在 0xF528，载荷缓冲区是堆地址（实测 0xa89eedb0）
```

协议 channel 表（运行期从 `/proc/<pid>/mem` 读 `0x17FD68` 得到）：

| ch | 描述符 | 名字 | 打包函数 |
|---|---|---|---|
| 0 | 0x0BA410 | `DJI V0 Protocol` | 0x15040 |
| 1 | 0x0BA44C | `DJI V1 Protocol` | 0x151A4 |
| 5 | 0x0BA3A0 | `DJI HOST Protocol` | 0x14410 |
| 6 | 0x0BA4E8 | `DJI V2 Protocol` | **0x16464** |

### 6.4 插桩是怎么做的（可复用）

`tools/bbxspy.c` 编成 `bbxspy.so`（约 2.7 KB），`LD_PRELOAD` 进 app.elf 拦 `sendto`。

- **必须 `-nostdlib` 裸 syscall**：雷达是 glibc 2.18，新工具链链出的 .so 带 `GLIBC_2.3x`
  版本符号，ld.so 直接拒绝加载。只用到 open(5)/write(4)/sendto(369)。
- 编译用 Vitis 自带的 `gnu/aarch32/nt/gcc-arm-none-eabi/bin/arm-none-eabi-gcc.exe`，
  `-O2 -fPIC -shared -nostdlib -mcpu=cortex-a9 -marm -fno-omit-frame-pointer`。
- 部署：kill 掉 `radar.autorun`（它会把 app 拉起来）→ kill app.elf →
  `LD_PRELOAD=/tmp/bbxspy.so nohup /home/root/app.elf &`，约 40 秒后才开始出 0x00F0。
  恢复：kill 掉再 `nohup /home/root/radar.autorun &`。

### 6.5 断在哪

栈回溯（48 字窗口 + 「前一条指令必须是 BL」过滤）只捞到两个真返回地址：
`0xF52C`（sendto 调用点）和 **`0x1333C`**（`0x13298` 里 `bl 0x11C8C` 之后）。

`0x13298` 的四个调用者（`0x2F040` / `0x2F0CC` / `0x2F124` / `0x5C704`）传的 payload
都只有 0x28 / 0x34 字节，**对不上 0x00F0 的 451~1099 字节** → 真正的黑盒 payload 是按指针传的，
还得再往上一层。

而这一层捞不到，是因为 **`0x13298` 自己的栈帧约 64 KB**，它的调用者返回地址在栈上
离 sendto 有 65 KB 远，48 字的扫描窗口根本够不到。

## 七、工程侧的三个坑（都踩过）

1. **`t40_bridge.py` 的 `iw` 没有超时**。`read_wifi()` 每 5 秒调一次
   `iw dev ... station dump`，ath6kl 一卡住就永久阻塞，发送线程挂在 `build_status()` 里。
   现象：TCP 46000 只剩 CAN 帧（0x10），没有 RADAR_UDP（0x20）也没有 STATUS（0x30），
   同时板卡 sshd 连得上 TCP 但不发 banner。**必须给 `iw` 加 timeout**。
2. **雷达 USB 很挑**。2026-11-10 遇到 `ath6kl: Failed to submit usb control message: -110`，
   反复枚举失败（`device descriptor read/64, error -110`），软件层 unbind/bind、
   `authorized` 掉电重上都救不回来，最后**断电重上雷达**才恢复。
   恢复后的正常日志是 `ath6kl: ar6004 hw 3.0 usb fw 3.5.0.349-1 api 5` + `wlx00037f2044d2`。
   注意雷达的 USB 接口类是 `ff`（厂商自定义），**没有串口可测**，判断依据只有这一行。
3. **设定转速不可信**。`radar_min.py --rpm 1200 --no-speed-relay` 起的进程，实测只有 905 rpm。
   任何跟转速相关的实验都必须先读 CAN 上的 `0x1E0F` 确认真实转速。

## 九、以后的方向

### 第一优先：把 builder 找出来（决定后面所有事）

**做法**：改 shim，把栈扫描窗口从 48 字放大到约 17000 字，并把
「前一条指令是 ARM BL」（`(w & 0x0E000000) == 0x0A000000`）这个过滤**直接写进 shim**，
只记录通过筛选的地址，最多 8 个。这样能越过 64 KB 的 `0x13298` 栈帧，
直接看到它的调用者——也就是真正把 12 字节记录填进去的那一层。

**代价**：需要再重启一次雷达 app（约一分钟没有数据）。
**产出**：builder 的函数地址 → 反汇编 → `c0..c5` 从哪个全局量取、有没有乘系数、有符号还是无符号。

### 第二优先：把「记录语义」钉死

拿到 builder 之后，用两组互相独立的证据交叉验证：

1. **静态**：builder 里每个字段的赋值来源；如果是 `float→u16` 的定点转换，比例因子会直接写在代码里。
2. **动态**：控制场景。把雷达对着已知距离的墙面（或者用手挡住某个方位），
   看哪个字段跟着距离变、哪个跟着方位变。这一步比任何统计都硬。

同时可以顺手做的验证：`c3` 最大值 7009 与文档里 20 m / 0.5 m 栅格、30 m 模式的关系；
`c0` 每帧固定 4173 tick 与一圈的对应关系。

### 第三优先：工程化收尾

- 给 bridge 的 `iw` 加 timeout（第一节的坑 1），否则一次 ath6kl 抽风就整条链路假死。
- `start_all.sh` 里 app 的拉起/守护理顺：现在 `radar.autorun` 一被杀，app 挂了就没人管。
- 雷达 USB 的稳定性：断电重上能恢复，但过程很难看；考虑在启动脚本里加一次
  「枚举失败就 rebind 重试」的兜底。

### 更远的目标（回到这个项目最初的目的）

项目要求最终是「XCZU3EG 出控制信号 + 收雷达信号 → 网口转发给电脑做后续处理」。
当前 0x00F0 的解是纯软件的旁路（借板卡的 Linux 抓），
真要做到「板卡自己产出点云」，还需要：

1. 记录语义定死之后，写一个能在板卡上跑的轻量解析器（Python 太慢，考虑 C），
   把 0x00F0 直接转成标准点云格式（PCD / 自定义二进制）走 UDP 发给上位机。
2. 再往后才是把 CAN 控制、雷达 UDP 收发、点云打包搬到 PL 侧（Vitis HLS / RTL），
   让 PS 只做调度。这一步的前提是记录格式完全确定，现在还不具备。

## 十一、记录字段：解出来了

### 11.1 怎么破的（这一步是关键）

第二节里 shim 只从自己的栈帧往上扫 48 个字（192 字节），而发送函数 `0x13298` 一上来就是

```
e92d43f0  push {r4-r9, lr}        ← 没有 r11，所以没有帧指针链可走
e24ddcff  sub  sp, sp, #0xFF00
e24dd0d4  sub  sp, sp, #0xD4      ← 合计 0xFFD4 ≈ 64 KB 栈帧
```

它的调用者的返回地址离 sendto 的栈帧有 65 KB，48 字的窗口根本够不到。

新版 `tools/bbxspy2.c` 换了个做法：**先把 `/proc/self/maps` 里包含当前 fp 的那个 mapping 的
`[start,end)` 读出来当上界，再把 `[fp, top)` 整段原始内存一次 write 进 `/tmp/bbxstack.bin`**，
离线用「这个地址前面那条指令是不是 BL/BLX」来筛真返回地址（栈上大量数据也会碰巧落在 .text 里）。
上界必须有——盲扫 96 KB 会越过栈顶踩到未映射页，把雷达 app 打死。

落盘格式（小端 u32）：`magic(0x42425358) ra len buf fd fp sp top nwords nchain`，
然后 `nchain` 个帧链地址，然后 `nwords` 个原始栈字。`tools/spy2_stack.py` 负责解。

### 11.2 拿到的调用链（全是尾跳转，所以 LR 一路不变）

```
0x307DC  F：构造一个 0x2c 字节的消息描述符（msg_id=0x00F0，常量 0x18/6/0xc8/0x1d/0x64）
   └ bl 0x14914 → b 0x1488C（按 (byte0,byte1) 查 0x11FF60 的 0x2c 步长路由表）
        └ b 0x135A8 → b 0x13530 → b 0x133C0 → b 0x13298（通用打包发送）
             └ 0x16464 → 0x16268 → 0x11C8C → 0xF4D0 → sendto@0xF528
```

`0x14914` 只是 `b 0x1488C` 的别名入口，不压栈；所以 `0x13298` 保存下来的 LR 就是
`0x30864`，也就是 F 里 `bl 0x14914` 的下一条。**F 才是这帧 0x00F0 的业务发起者。**

### 11.3 再往下：payload 是个全局地址

F 的四个调用者里，唯一真正发 0x00F0 的那个在 `0x4CE58`：

```
0x4CE24  ldr   r2, [pc, #0x250]     ; r2 = 0x0C442FB8（body 缓冲区）
0x4CE30  ldrb  r0, [r2, #1]!        ; 对 body+1..body+16 累加
0x4CE48  strb  r3, [r4, #0x1a]      ; → 头部校验和
0x4CE50  ldr   r1, [sp, #0x28]
0x4CE54  add   r0, r5, #8           ; r5 = 0x0C442FB0
0x4CE58  bl    0x307DC              ; ← 把全局缓冲区当 payload 交给 F
```

于是 `0x0C442FB8` 就是 0x00F0 的 body（19 字节头 + 记录区），从 `/proc/<pid>/mem` 读出来
和线上抓的包逐字节对得上。

### 11.4 记录写入函数 `0x4CBF8` 读的三个源数组

| 东西 | 地址 | 规模 | 用途 |
|---|---|---|---|
| 索引表 | `0x0C451A30` | 10000 × u16 | `tv = table[phase*5000 + i]`，实测就是 0,1,2,… |
| 源数组 A | `0x0C456850` | 10000 × 12 B（3×float） | 角度、角度、距离 |
| 源数组 B | `0x0C473D10` | 10000 × 12 B（3×float，用前 2） | 幅度类 |
| 源数组 C | `0x0C4911D0` | 10000 × 12 B（用第 1 个 u32） | µs 时间戳 |
| body 缓冲 | `0x0C442F90 + 0x28` | — | 19 B 头 + N×12 |
| 计数 | `0x0C451A2C` | u16 | `c5` 的基准 |

三个数组间距都是 `0x1D4C0`（10000×12），索引表在 A 前面 20 KB。

### 11.5 公式（逐寄存器追出来的，带整数截断）

```
tv = table[base + i]
c0 = (u16)(A[tv].x * 1000)              // s10 = 1000.0
c1 = (u16)((A[tv].y + 2π) * 1000)       // s8 = 6.28319
c2 = (u16)(A[tv].z * 1000)
c3 = (u16)(B[tv].x / 100)               // s9 = 100.0
c4 = (u16)(B[tv].y / 100)
c5 = (u16)(C[tv] - count)
```

对应指令（`0x4CD50`–`0x4CDD8`）：`vmul.f32 s11,s11,s10` / `vadd.f32 s15,s15,s8` /
`vdiv.f32 s13,s13,s9` / `vcvt.u32.f32` / `strh`。

### 11.6 验证：三条独立证据

**① 单条记录五字段全中**（同一次内存快照）：
`A[tv]=(5.1813, −0.28502, 36.7588)`、`B[tv]=(4954, 1654)` → 记录 `[5181, 5998, 36758, 49, 16]`，
误差 0。(−0.28502+2π)×1000 = 5998 ✓）

**② c0 是方位角、c5 是时间**：逐帧算 `corr(c5, c0)`，**2766 帧全部 = 1.00**（见 `captures/c5c0.png`），
c0 随 c5 严格线性增长。再用斜率反算转速：

| 项目 | 值 |
|---|---|
| 斜率 | 4.17 rad / 43 ms |
| 反算转速 | **926 rpm**（p5–p95 = 926–931） |
| 当时 CAN 实测 | **905 rpm** |

同量级、差 2.3%（c5 的时间单位可能不是严格 1 µs，或实测转速本身有偏差），足以定性。

**③ c2 是距离**：0x00F0 的 `c2/1000` 分布（p75=44.2 m、p95=58.8 m）与同一份抓包里
**1E61 地面点**的距离分布（p5=35.3、p50=49.4、p95=61.2 m）落在同一个区间；
另外还有一根 1.3–1.6 m 的近场尖峰（8.3 万条，占一半），是雷达正下方的地面/机体回波——
1E61 那串距离/仰角过滤器把它滤掉了，正好解释了两者 9.9:1 的点数比。

### 11.7 结论表

| 字段 | 含义 | 单位 | 值域（180 s 实测） |
|---|---|---|---|
| `c0` | **方位角**（旋转头的角度） | mrad | 1031–5228 |
| `c1` | **俯仰角**，存的是 `(el + 2π)` | mrad | 5249–7204（减 6283 得 −1.03…+0.92 rad） |
| `c2` | **距离** | mm（u16 在 65.5 m 回绕） | 1268–62771 |
| `c3` | 回波幅度（源 float÷100） | 0.01 | 8–7009 |
| `c4` | 次幅度量 / SNR（源 float÷100） | 0.01 | 3–657 |
| `c5` | 探测时刻（绕内时间偏移） | µs | 10146–53271 |

`c3`/`c4` 随距离的走势是先升后降（0–3 m: 70/11 → 10–20 m: 404/340 → 50–65 m: 53/16），
是典型的近场饱和 + 远场滚降，符合幅度/信噪比的物理形状；两者比值随距离从 0.85 掉到 0.3。

### 11.8 19 字节 body 头（旧表，已被第二轮更正）

> **2026-11-10 第二轮更正**：下面按 u8/u16 拆开看是错的。`+5..8` / `+9..12` 是
> **两条 u32 微秒时间戳**，`+17` / `+18` 是**两个 u8 累加校验和**（`sum8(记录区)`、
> `sum8(头[1..17])`），`+15` = `head+1`、`+16` = `ceil(点数/5000)`。
> 两份抓包共 3686 帧逐帧验证通过，详见
> 《T40雷达0x00F0头部与源数组补全_2026-11-10.md》。

| 偏移 | 内容 |
|---|---|
| +0..2 | 常量 `03 10 07` |
| +3 | u16 帧序号，每帧 +1 |
| +5 / +6 | 未解（+6 缓慢递减） |
| +7 | u16 计数器 +1 |
| +9 | u16，两档跳变 |
| +11 | u16 计数器 +1 |
| +13 | **u16 记录区字节数 = N×12** |
| +15 / +16 | `01 01` |
| +17 | u16 未解 |
| +19 | 记录区开始 |

### 11.9 现在能做什么

`tools/bbx_decode.py` 直接吃 `bbx_capture.py` 落的 JSONL，把每帧切成记录并出统计/CSV/图：

```bash

```

### 11.10 还剩下的（都不影响出点云 · 第 1/2/3/4 项已销项）
