# T40 雷达 0x00F0：头部字段与源数组来源补全（2026-11-10 第二轮）

配合《T40雷达0x00F0逆向总结_2026-11-10.md》第十一节使用。那一节已经把 12 字节记录的
6 个 u16 解出来了，但 11.8 的头部表还是旧的（标着「未解」），11.10 也留了几个 open item。
这一轮把**头部的每一个字节**、**A/B/C 三个数组的上游**、**c5 的单位标定**全部补齐，并且
都用抓包做了逐帧硬验证，不是推测。

---

## 一、结论速览

| 之前的状态 | 现在 |
|---|---|
| 头部 `+5/+6/+9/+17` 未解 | `+5..8`、`+9..12` 是**两条 u32 微秒时间戳**；`+17`、`+18` 是**两个 u8 累加校验和** |
| 「c5 的时间单位值得再标定」 | 单位**精确 = 1 µs**（帧间增量与板卡单调时钟比值 0.999992）；`c5` 是帧内 µs 偏移 |
| 「A/B/C 是谁填的没找到」 | 找到上游：`0x4CA7C` 从 `0xC3C1940 / 0xC4233C0 / 0xC419780` 拷进来；再上游是 DSP 解码循环 `0x4C8D8` |
| 「c1 的 +2π 符号方向要实测」 | 代码 `0x4C918 vsub.f32 s15,s15,s17` 直接减去 2π，方向已定：**记录里存的是 `el + 2π`**，不用再实测 |
| 「+15/+16 = 01 01 常量」 | 不是常量，是 `head+1` 与 `ceil(点数/5000)`，只是常态都等于 1 |

## 二、19 字节头：逐字节、带写入指令

`body` 在全局 `0x0C442FB8`（= `0x0C442FB0 + 8`），头部各字节由 `0x4CF50`–`0x4CFA8`
这段写进去：

| 偏移 | 类型 | 含义 | 写入指令 / 来源 |
|---|---|---|---|
| +0..2 | u8[3] | `03 10 07` 常量 | `0x4CF68/74/7C`：`strb 3/0x10/7` |
| +3..4 | u16 | 帧序号，每帧 +1 | `0x4CF70 strh r0,[r4,#0xb]`，源 `[0x0C442FB2]` |
| +5..8 | **u32** | 时间戳 A（µs） | `0x4CF64 str r8,[r4,#0xd]`，源 `[0x0C49AE14]` |
| +9..12 | **u32** | 时间戳 B（µs） | `0x4CF50 str r2,[r4,#0x11]`，源 `[0x0C451A2C]` |
| +13..14 | u16 | 记录区字节数 `N×12` | `0x4CDF4 strh r2,[lr,#0x15]` |
| +15 | u8 | 环形缓冲 `head+1`（常态 1） | `0x4CCA4 strb r2,[r4,#0x17]` |
| +16 | u8 | `ceil(点数/5000)`，批数（常态 1） | `0x4CFA8 strb r2,[r4,#0x18]` |
| +17 | u8 | `sum8(记录区)` | `0x4CE0C..0x4CE1C` 逐字节累加 |
| +18 | u8 | `sum8(头[1..17])` | `0x4CE24..0x4CE48` 对 `body+1..+17` 累加 |

之前把 `+5/+6/+7` 拆成 u8/u8/u16、`+9/+11` 拆成两个 u16 看，才会出现
「`+9` 每帧 −488 或 −397、`+11` 每帧 +1」这种诡异现象：**它其实是 u32 的低 16 位
每帧加 ~65000 µs 后回绕，高 16 位收到进位 +1**。`65536−65048 = 488`、
`65536−65139 = 397`，正好对上原来的两个观测档。

`+17` 之前当成 u16 高熵字段，其实是两个独立 u8 校验和拼在一起；`+15/+16` 同理不是
魔数常量。

### 硬验证（`tools/bbx_hdr_verify.py`）

| 检验 | 180 s / 905 rpm（2766 帧） | 30 s / 1800 rpm（920 帧） |
|---|---|---|
| `+17 == sum8(记录区)` | **2766 / 2766** | **920 / 920** |
| `+18 == sum8(头[1..17])` | **2766 / 2766** | **920 / 920** |
| `+13 == N×12` 且长度自洽 | 2766 / 2766 | 920 / 920 |
| `+3` seq 每帧 +1 | 2765 / 2765 | 919 / 919 |
| `+15/+16 = 01 01` | 2766 / 2766 | 920 / 920 |
| 帧内 `c5` 单调不减 | **2766 / 2766** | **920 / 920** |

### 时间戳单位 = 1 µs（这条最硬）

| 采集 | 头部 u32@+9 帧间均值 | 板卡 `monotonic_ns` 帧间均值 | 比值 |
|---|---|---|---|
| 180 s / 905 rpm | 65085.2 µs | 65085.7 µs | **0.999992** |
| 30 s / 1800 rpm | 32656.0 µs | 32656.3 µs | **0.999852** |

两档帧周期之比 `65085.7 / 32656.3 = 1.993`，跟转速比 `1800/905 = 1.989` 一致 ——
又独立印证了「一转一圈一帧」。两条 u32 时间戳全程跨度 179.9604 s / 179.9606 s
（采集 180 s）、30.0064 s / 30.0067 s（采集 30 s），都是 1 MHz 计数。
`ts_a − ts_b` 约 2.9 s 且不同会话略有变化（2.945 s / 2.915 s），是两条独立时钟，
不是同一个值的两次拷贝。

## 三、A/B/C 三个数组的上游（把 11.10 第 4 项销掉）

`0x4CA7C` 是个「快照函数」：按 `ldrh [0x0C442F90]` 给出的点数 `count`，把 6 份原始数组
**memcpy 到调用者给的目的地**。调用点在 `0x4CEC4`，目的地址来自字面池 `0x4D070..0x4D084`：

| 快照目的地（内存 dump 里的区） | 原始源数组 | 每条长度 | 内容 |
|---|---|---|---|
| `0x0C456850`（A） | `0x0C3C1940` | 12 B | `(方位 rad, 仰角 rad, 斜距 m)` |
| `0x0C473D10`（B） | `0x0C4233C0` | 12 B | `(幅度×100, 次幅度/SNR×100, 每帧常量)` |
| `0x0C4911D0`（C） | `0x0C419780` | 4 B | 每点一个 u32 µs 时间戳 |
| 另外三份（未进 12B 记录） | `0x0C3FC2C0` / `0x0C3DEE00` / `0x0C3B2EE0` | 12/12/6 B | 变换后笛卡尔坐标等 |

**这些常量只在 `0x4C570..0x4C580` 和 `0x4CBA0..0x4CBB8` 两组字面池里出现**，所以上一轮
「全镜像里只有读取端引用」的印象是错的：写入端用的是 `movw/movt` 拼地址再经寄存器间接写，
搜 32 位常量自然搜不到。

### 上游的 DSP 解码循环 `0x4C888..0x4C9F4`

它读一份**同为 12 字节 / 6×u16 的原始记录**，反解成浮点：

```
az  = raw0 / 1000                     ; s16 = 1000.0
el  = raw1 / 1000 - 2π               ; 0x4C918 vsub s15,s15,s17，s17 = 2π
R   = raw2 / 1000                     ; 米
→ 0x422C8(az, el, R)                 球坐标 → 笛卡尔
→ 0x4216C ×2                         两个 3×3 旋转矩阵（姿态/坐标变换）
→ 0x0C3FC2C0                         变换后的 (x,y,z)
→ 0x0C4233C0 = (raw3×100, raw4×100, 每帧常量 s18)
```

`0x422C8` 里两次 `sincos` + 三次 `vmul` 明确是
`x = R·sin(el)·cos(az), y = R·sin(el)·sin(az), z = R·cos(el)`；
`0x4216C` 是标准 3×3 矩阵乘（`vldr` 从 `[r1+0..0x20]` 取 9 个 float）。

这条链把物理命名闭环了：**`c0` 方位角、`c1` 仰角、`c2` 斜距、`c3/c4` 幅度类**，
不是靠量纲猜的。而且 `el = raw1/1000 − 2π` 直接确定了 `+2π` 的符号方向：
记录里存的是 `el + 2π`（`el` 可为负，加 2π 保证 u16 非负），解析时减回去。
`0x00F0` 实际是「原始 u16 记录 → 内部浮点点云 → 重新量化打包」的结果。

顺带解掉两个小疑问：
- B 数组第 3 个 float（`9260/9760/11150`）是**每帧一个常量**（`s18` 来自 `[sl+0xb]`），
  不进 12 字节记录，之前按「块内恒定」猜它是时间戳是不对的。
- `c5` 的基准不是 c0×常数：`0x4CD80 rsb r6,r0,r6` = `C[tv] − low16(ts_b)`，
  即「该点时间戳 − 本帧时间戳」的低 16 位，65.536 ms 回绕一次。
  这就是它在**每一帧内都单调不减**（2766/2766 + 920/920）的原因，
  也解释了为什么它看起来跟 c0 线性相关（方位角本来就是随时间扫的）。

## 四、对第十一节遗留项的销项

| 11.10 里的遗留项 | 状态 |
|---|---|
| 1. `c1` 的 +2π 符号方向需实测 | **已定**：`0x4C918` 明确减 2π，记录里存 `el+2π`；无需实测 |
| 2. 头部 +5/+6/+9/+17 未解 | **已解**：两条 u32 µs 时间戳 + 两个 u8 累加校验和，逐帧验证通过 |
| 3. c5 时间单位需标定 | **已标定**：精确 1 µs；与板卡单调时钟比值 0.999992 / 0.999852 |
| 4. A/B/C 是谁填的没找到 | **已找到**：`0x4CA7C` 的 memcpy 源 + `0x4C888` DSP 解码循环 |

还剩的小问题（都不影响出点云）：
`ts_a / ts_b` 两个时钟各自对应哪个时间域（相差约 2.9 s，随会话变化）；
`c3` / `c4` 谁是 `power` 谁是 `snr`（type descriptor 里 `radar_point_cloud{power,snr}`
的两个 uint32 与之对应，但没有写入端的直接证据）；
`c2` 在 65.536 m 回绕时如何区分「远点」与「绕回」；
`c0` 跨 0 的处理（实测值域 1031–5228 mrad，未见跨 0）。

## 五、复现

```bash
# 头部逐帧硬验证（两份抓包都跑）
python tools/bbx_hdr_verify.py captures/bbx_180s.jsonl captures/bbx_1800rpm_30s.jsonl

# 记录级解码 / 出点云 CSV（已有工具）
python tools/bbx_decode.py captures/bbx_180s.jsonl --csv /tmp/bbx.csv --plot /tmp/bbx.png

# 整段栈 dump 找 builder（v2 shim 的产物）
python tools/spy2_stack.py captures/bbxstack.bin captures/app.elf
```

`spy2_stack.py` 在 4 个样本里稳定给出 `0x0F52C → 0x1333C → 0x30864 → 0x4CE5C`，
后两个就是越过 64 KB 栈帧之后才看得见的业务层返回地址。

数据依据：`captures/bbx_180s.jsonl`（2766 帧 / 160936 条记录）、
`captures/bbx_1800rpm_30s.jsonl`（920 帧）、`captures/memdump*.txt` / `snap12.txt`
（12 组内存快照）、`captures/app.elf`（md5 `0d33f0dfbc5fc00f711362fcc56ef307`）。
